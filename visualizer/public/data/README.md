# GPS and GPX visualization examples

## Halifax fixture

`halifax-gpx.arrows` and `halifax-gpx.arrows.names.arrow` are a small, checked-in
artifact generated by the production `soloc-ledger` GPX playback exporter. They
load without kernels in the browser and are mandatory inputs to frontend tests;
those tests fail if the files are absent.

The source is [halifax.gpx](../../../crates/soloc-ledger/tests/fixtures/gpx/halifax.gpx):
five **simulated** positions near Halifax in two disconnected segments, with explicit
WGS84 ellipsoidal elevations and UTC timestamps on January 1, 2025. The exporter
keeps those observations in ITRF93 metres, normalizes their instants to TAI, and
adds nine ITRF93→GCRF orientation samples. Four embedded provenance columns preserve
segment/point continuity; the names sibling is cosmetic.

Generated October 21, 2026 using ANISE 0.10.6 and the locally cached
`earth_latest_high_prec.bpc`, SHA-256:

```text
f95a7fed588a6614f53ed28cee15eb9148abaf808739f94f0c62de935a82edbb
```

The BPC is not bundled. Regenerate from the repository root with an explicitly
supplied Earth BPC covering the example interval (no downloads):

```bash
SOLOC_KERNEL_PATHS=/path/to/earth_latest_high_prec.bpc \
  cargo run -p soloc-ledger --features gpx --example export_gpx -- \
  visualizer/public/data/halifax-gpx.arrows
npm --prefix visualizer test
```

A different kernel revision can produce slightly different orientation samples.
Tests check geometry, time alignment, rotation direction, retained rows and gap
behavior; they do not certify the underlying Earth model or freeze its bytes.

Run `npm --prefix visualizer run dev`, then open
`http://localhost:5173/?src=/data/halifax-gpx.arrows`, or select/drop both files.
Click **halifax-vessel** to focus the route. Between 12:00:57 and 12:05:37 **TAI**,
the marker is absent and the inspector reports an observation gap. The second
trail begins only when its observations are reached. The Earth surface is a WGS84
ellipsoid; mesh triangles and map imagery are visual approximations, so assess
metre-level heights numerically rather than from apparent mesh clearance.

## Ottawa–London simulated flight

`ottawa-london-flight.arrows`, its `.names.arrow` sibling, and
`ottawa-london-flight.gpx` are generated by the reproducible
[export_flight example](../../../crates/soloc-ledger/examples/export_flight.rs).
The Arrow files open directly in the existing visualizer; the GPX is the generated
input passed through the production GPS converter and playback exporter.

This is a **synthetic demonstration**, not a recorded or scheduled airline flight:

- Ottawa International (YOW) → London Heathrow (LHR), one continuous GPX segment.
- January 1, 2025, **12:00–19:00 UTC**; the viewer displays **12:00:37–19:00:37 TAI**.
- **421 observations**, one every 60 seconds including both endpoints, plus
  **421 ITRF93→GCRF frame poses**: 842 rows in the exported ledger.
- An illustrative great-circle path on a sphere, expressed as WGS84 geodetic
  latitude/longitude. This is not a computed WGS84 ellipsoidal geodesic or an airway.
- Smooth 30-minute climb to **11,000 m**, six-hour cruise, and 30-minute descent.
  All heights are explicitly synthetic WGS84 **ellipsoidal** heights, including
  150 m at departure and 100 m at arrival; they are not airport elevations or
  pressure altitudes. There is no geoid or terrain correction.
- Poses are `SIMULATED` with conventional `LocalEnu` orientation. Aircraft
  attitude and velocity are not inferred from the path; optional kinematics remain null.

The illustrative airport endpoints are the location published by
[Ottawa Airport](https://www.yow.ca/about-yow/contact-us)
(45.32427° N, 75.6627° W) and the reference point published in
[Heathrow’s crane-operation guidance, Appendix A](https://www.heathrow.com/content/dam/heathrow/web/common/documents/company/team-heathrow/airside/operational-safety-insttructions/ASWorks_OSI_003%20Procedure%20for%20Approving%20the%20Operation%20of%20Cranes%20and%20Other%20Tall%20Equipment_v3.pdf)
(51.477581° N, 0.46137241° W). These locate the airports; the simulated track
does not model runway alignment, taxiing, actual departure/arrival procedures,
weather or a particular aircraft.

### View the flight

From the repository root, run:

```bash
npm --prefix visualizer run dev
```

Paste this address directly into the browser address bar (keep the `=` literal):

```text
http://localhost:5173/?src=/data/ottawa-london-flight.arrows
```

Use **Earth overview** and rotate the globe toward the North Atlantic. Choose
**1 h/s** and press Play for a seven-second replay, or scrub the timeline for
individual points. The trail shows elapsed observations; drag to the end to see
the complete path. **1 min/s** takes seven minutes to show the full flight.
Click **ottawa-london-flight** to inspect an individual position and its GPX
provenance; that close-up is better for a paused sample than a full-route view.

Alternatively, load both `.arrows` files with the file picker or drag-and-drop.
Opening an already-generated export requires no local kernels or Rust build.

### Regenerate

The example requires an explicit local Earth BPC covering the entire flight;
it performs no kernel downloads. From the repository root:

```bash
SOLOC_KERNEL_PATHS=/path/to/earth_latest_high_prec.bpc \
  cargo run --locked -p soloc-ledger --features gpx --example export_flight -- \
  visualizer/public/data/ottawa-london-flight.arrows
```

The output path is optional and defaults to the path above. The command saves the
generated GPX beside the Arrow file and its display-name sidecar. The checked-in
export uses the same local BPC snapshot and SHA-256 documented for Halifax above.
The date and route parameters are defined in the Rust example. Changing the
journey requires regenerating the output and ensuring kernel coverage. Bounded
import batches do not limit the total memory needed to retain the complete export.

## Sedona single estimated GPS observation

`sedona-single-gps.arrows` and its `.names.arrow` sibling contain one estimated
GPS observation at **34.8697° N, 111.7611° W**, plus one ITRF93→GCRF frame pose at
the same instant. This uses the single-fix converter and standard EntitySchema;
there is no GPX track or invented GPX provenance. Exact values and assumptions are
in `sedona-single-gps.json`.

The supplied elevation was approximately **1,326 m above mean sea level**.
For this demonstration it is treated as approximately EGM96 orthometric height:
`h = H + N = 1326 - 24.53045742765352 = 1301.4695425723464 m` above the WGS84
ellipsoid. The original elevation datum is unknown; this is an explicit estimate,
not an identification of the photo's exact location or height. The geoid value
comes from bilinear interpolation of the local PROJ `egm96_15.gtx` grid,
SHA-256 `c02a6eb70a7a78efebe5adf3ade626eb75390e170bb8b3f36136a2c28f5326a0`.
The height relation is documented by
[GeographicLib](https://geographiclib.sourceforge.io/html/GeoidEval.1.html);
[PROJ's vertical-grid transformation](https://proj.org/en/stable/operations/transformations/vgridshift.html)
independently reproduces the value:

```bash
printf '%s\n' '-111.7611 34.8697 1326 2025' | \
  cct -d 9 +proj=vgridshift +grids=/usr/share/proj/egm96_15.gtx +multiplier=1
```

The actual observation time is unknown, so the example assigns **2025-01-01
12:00:00 UTC**, shown as **12:00:37 TAI**. This is a single instant, not a replay
interval. Orientation is conventional local east/north/up, not camera attitude;
velocity and covariance remain unknown. The Earth map is an ellipsoid with
imagery, not a terrain model of Sedona.

From the repository root:

```bash
SOLOC_KERNEL_PATHS=/path/to/earth_latest_high_prec.bpc \
  cargo run --locked -p soloc-ledger --example export_sedona -- \
  -24.53045742765352
npm --prefix visualizer run dev
```

Open `http://localhost:5173/?src=/data/sedona-single-gps.arrows`, or load the Arrow
file and its names sibling together. **Earth overview** shows the globe;
**sedona-observation** selects the point and its exact row values. Regeneration
requires an Earth BPC covering the assigned instant; opening the generated files
does not. The export uses the same local BPC snapshot recorded above.
